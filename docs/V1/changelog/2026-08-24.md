### F1. 思考模式 reasoning_effort 字段位置错放（后端 / llm.js）

- 现象：用户在 UI 选"中"或"高"档后，问问题聊天页 **看不到** `💭 LLM思考过程` 折叠项，`delta.reasoning_content` 始终为空字符串。
- 根因：`buildThinking(reasoningConfig)` 错误地把 `reasoning_effort` 嵌套在 `thinking` 对象内：
  ```js

  { thinking: { type: 'enabled', reasoning_effort: 'medium' } }
  // 正确：reasoning_effort 必须与 thinking 平级
  { thinking: { type: 'enabled' }, reasoning_effort: 'medium' }
  ```
  DeepSeek 官方文档（[create-chat-completion](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion)）明确把 `reasoning_effort` 放在请求体顶层。
- 修复：改用 spread 展开，让 `thinking` 和 `reasoning_effort` 平级；修复后 `delta.reasoning_content` 流式返回非空。
- 提交：`3126dba`；后端 `--watch-path=src` 自动重载生效。

### F8. `currentFlowSessionId` ReferenceError：let 声明在 try 块内（前端 / App.jsx）

- 现象：console 抛 `Uncaught (in promise) ReferenceError: currentFlowSessionId is not defined at handleSend (App.jsx:1022)`；同时切回正在流式输出的会话时，聊天记录不更新（看不到正在转圈的图标），必须反复切会话才能看到新内容。
- 根因：
  1. `currentFlowSessionId` 用 `let` 在 `try` 块内声明，`finally` 块在 `try` 块外访问 → TDZ 错。
  2. `useEffect([currentSessionId])` 无条件调用 `loadMessages(currentSessionId)`，**会覆盖正在流式累积的 `messagesBySession[currentSessionId]`** —— 切到 B 切回 A 时，A 还没落库的最新 chunk 被 `loadMessages` 拉回的历史覆盖。
- 修复：
  1. `let currentFlowSessionId = flowSessionId` 移到 `try` 块外声明；
  2. useEffect 加守卫 `if (streamBatchesRef.current[currentSessionId]) return;` —— 正在流的会话跳过 `loadMessages`。
- 提交：源码改动（未提交）；前端 build 验证。

### F10. done 事件 token 累加 + meta 事件会话跳转污染其他会话（前端 / App.jsx）

- 现象：A 会话在流，用户切到 B；A 的 done 事件到达时 `setCurrentTokens` 仍把 A 的 token 累加到 currentTokens（虽然 B 已切走但 currentTokens 是单值 state）。同时 meta 事件触发 `setCurrentSessionId(newId)` 时，**会把用户从 B 拽回 A**（新会话 id 不等于 currentSessionId 时无条件跳转）。
- 根因：
  1. `setCurrentTokens(prev => prev + data.totalTokens)` 没判断 `currentSessionId === currentFlowSessionId` → 任意会话完成都累加到当前显示值。
  2. meta 事件 `if (data.sessionId !== currentFlowSessionId) ... if (newId !== currentSessionId) setCurrentSessionId(newId);` → 用户已切到 B 后 A 的 meta 到达，仍会把视图跳回 A。
- 修复：
  1. done 事件 token 累加加 `currentSessionId === currentFlowSessionId` 守卫；
  2. meta 事件 `setCurrentSessionId(newId)` 改为 `if (!currentSessionId && newId) setCurrentSessionId(newId)` —— 只在"用户从未选过会话"时跳转。
- 提交：源码改动（未提交）；build 验证。

### F11. B 看 A 在流时点 B 的"停止"按钮误杀 A（前端 / App.jsx + ChatInput.jsx）

- 现象：A 在流，用户切到 B，B 输入框右侧显示"停止"按钮（红色转圈）；用户点 B 的"停止"按钮 → A 的流被中断。abort 行为虽然"正确"（全局只 1 个活跃流），但 UX 违反直觉：用户以为停的是 B，结果停的是 A。
- 根因：
  1. `loading` 是全局流状态（A 在流时 B 也是 true）；
  2. `ChatInput` 用 `loading` 判断显示"停止"按钮 → A 在流时切到 B，B 顶部按钮也是停止；
  3. 即便 `handleStop` 已改为"abort 全局唯一活跃流"（保证只杀一个），UI 仍把按钮放在 B 顶上。
- 修复：
  1. App.jsx 新增 `streamingSessionId` state，handleSend 入口设、finally 清（`prev === currentFlowSessionId ? null : prev` 防御性守卫）；
  2. handleDeleteSession 删的是"正在流的会话"时显式清 `streamingSessionId`（finally 在 fetch abort race window 可能不执行）；
  3. ChatInput 改 prop：`loading` → `isCurrentSessionStreaming`（= `currentSessionId === streamingSessionId`）+ `otherSessionStreaming`（= `loading && !isCurrentSessionStreaming`）；
  4. 按钮条件：`isCurrentSessionStreaming ? 停止 : 发送（disabled by otherSessionStreaming）`；
  5. TextArea disabled：`disabled || isCurrentSessionStreaming || otherSessionStreaming`；
  6. placeholder 3 态：弹窗阻塞 / 当前会话在流 / 其他会话在流 / 正常。
- 新行为矩阵：

| 场景 | 当前会话 | 按钮 | TextArea | placeholder |
|---|---|---|---|---|
| A 流中 | A | 停止（可点）| disabled | "当前会话正在生成中，点右侧停止按钮中断" |
| A 流中 | B | 发送（disabled）| disabled | "另一会话正在生成中，请等待其结束" |
| 都没流 | 任意 | 发送（可点）| enabled | "输入自然语言查询…" |

- 提交：源码改动（未提交）；build 验证。

### O16. 多会话并行流式管理（前端 / App.jsx，核心架构重构）

- 背景：旧实现 `messages` 是单数组 + `streamRequestIdRef` + `abortControllerRef`，**流式输出时切会话会被中断**。用户希望：A 在流式输出时切到 B，**A 后台继续跑**，B 也能正常看历史/提问；**全局同时只允许 1 个 LLM 流**（避免双跑抢资源）。
- 重构：
  1. `messages` 单数组 → `messagesBySession: { [sessionId]: Message[] }`；
  2. 派生 `messages = currentSessionId ? messagesBySession[currentSessionId] || [] : []`；
  3. `streamRequestIdRef` / `abortControllerRef` 替换为 `streamBatchesRef: { [sessionId]: { controller, version, isLoading } }`；
  4. `isGlobalStreamingRef: boolean` 全局守卫，handleSend 入口 `if (isGlobalStreamingRef.current) { warning; return; }`；
  5. SSE 回调按 `currentFlowSessionId` 写入 `messagesBySession[currentFlowSessionId]`，**与 UI 视图的 `currentSessionId` 解耦**；
  6. handleStop 找全局唯一活跃流（`Object.keys(streamBatchesRef.current)[0]`）abort；
  7. handleSessionClick 移除"切会话时 abort"逻辑；后台流继续跑；
  8. meta 事件迁移 `messagesBySession[oldId] → [newId]` + `streamBatchesRef[oldId] → [newId]`（后端权威 sessionId 可能与前端临时 id 不同）；
  9. `handleDeleteSession` 同时清 `streamBatchesRef[sessionId]` + `messagesBySession[sessionId]` + 必要时 `abort controller`。
- 关键设计：
  - **流状态双轨**：`loading`/`isStreaming`（全局流标志，给 UI 兜底）+ `streamingSessionId`（具体在流的 sessionId，给 ChatInput 决定按钮态）—— 见 O20。
  - **"自己是最新流"守卫**：`myStreamVersion` 闭包变量，SSE 回调顶部 `if (batch.version !== myStreamVersion) return;` 防止旧流乱写新数据。
  - **finally 清理**：`streamBatchesRef[flowSessionId]` + `roundUsagesRef[flowSessionId]` + `abortControllerRef` 一起清；用 `batch.version === myStreamVersion` 守卫避免误清新流。
