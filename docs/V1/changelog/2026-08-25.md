## C. 功能修复：改模型后聊天页模型标签不更新（前端 / ConfigPanel.jsx + App.jsx）

- 现象：在配置面板切换模型并保存后，聊天输入框下方的模型名标签（`ChatInput.jsx:314`）仍是旧值，要刷新页面才更新。
- 根因：聊天页模型显示的数据源是 `App.jsx` 里 `useAppConfig` 的 `currentModel`，仅在应用挂载时通过 `loadCurrentModel()` 加载一次（App.jsx:257，有 `initialLoadRef` 守卫）；`ConfigPanel.saveLlm()` 保存成功后只刷新面板自身 state，无任何机制通知 App。
- 修复：
  1. `ConfigPanel.jsx` 新增两个可选回调 prop：`onLlmConfigSaved`（saveLlm 成功后触发）、`onAgentConfigSaved`（saveAgent 成功后触发——同类问题：token 警告阈值改后进度条阈值也是旧的）；
  2. `App.jsx` 渲染处传入 `onLlmConfigSaved={loadCurrentModel}`、`onAgentConfigSaved={loadAgentConfig}`；
  3. **顺带修复同文件真 bug**：`testDb` / `saveDb` 使用了未定义变量 `message[...]`（应为 `messageApi`），ReferenceError 被 catch 吞掉导致"测试连接"无论成败永远提示"连接失败"；改为 `messageApi` 并正确透传后端消息。
- 验证：`npm run build` 通过；手动场景——打开配置 → 切模型 → 保存 → 聊天页模型标签立即变为新值；Agent 阈值同理。

## B. 功能修复：file_storage 存绝对路径不可移植（后端 / files.js + sqlite.js + index.js）

- 现象：用户指出 `file_storage.file_path` 存的是**绝对路径**（如 `D:\...\backend\file_cache\file-api-xxx`）。项目挪目录 / Electron 便携模式换盘符 / 换机器部署后，全部索引失效，历史图片回显退化为 404。
- 根因：`writeStorage` 直接把 `join(FILE_CACHE_DIR, fileId)` 的绝对路径写进 DB。而缓存目录是扁平结构（`file_cache/<file_id>`），路径完全可由 file_id 推导——DB 根本不需要存绝对路径。
- 修复（A10 v3）：
  1. `services/files.js` 新增 `resolveStoragePath(filePath)`：相对文件名 → `join(FILE_CACHE_DIR, file_path)`；兼容历史绝对路径行（原样使用）；
  2. `writeStorage` 改存**相对文件名（=file_id）**；
  3. `readStorage` / `removeStorage` 统一走 `resolveStoragePath` 解析；
  4. 新增 `migrateFileStorageRelativePaths()`：启动时幂等批量把存量绝对路径行规范化为文件名（事务 + log 记录迁移条数；失败仅 warn 不阻塞启动）；
  5. `index.js` 启动序列在 `ensureFileCacheDir()` 后调用迁移；`db/sqlite.js` schema 注释同步。
- 兼容性：迁移前老行仍可读（resolveStoragePath 兼容绝对路径），迁移后与磁盘实际位置解耦。
- 测试：新增 `test/test-file-storage-relative-path.mjs`（7 断言：绝对路径规范化 / 相对行不动 / 幂等 / 空表 no-op）；全量 `node --test` **29/29 通过**。
- **清理（同日，用户启动验证后）**：
  - 实测启动一次后 `file_storage` 2 行全部变为相对文件名（`[REL] file-api-f0fb8504-...` / `file-api-a7f940c7-...`），磁盘文件 + meta 齐全；
  - 按约定删除一次性迁移功能：`files.js` 删 `migrateFileStorageRelativePaths()` + `resolveStoragePath` 去掉绝对路径兼容分支（简化为纯 `join`）、移除 `basename/isAbsolute` import；`index.js` 删调用与 import；删除测试 `test/test-file-storage-relative-path.mjs`；`sqlite.js` schema 注释同步；
  - `files.js` 保留历史注记注释说明迁移已发生并删除，防止后人困惑"为什么没有迁移逻辑"；
  - 全量回归 `node --test` **28/28 通过**。
- **v4：彻底去掉冗余 file_path 列（用户指出 file_id 与 file_path 数据完全相同）**：
  - `db/sqlite.js`：新 schema 仅 `file_id PK + mimetype/bytes/saved_at`；启动时检测老表含 `file_path` 列 → 事务内建新表拷数据 → 原子替换（数据保留，回显不断档）；顺带修正古老 BLOB 迁移的顺序问题（原代码 DROP 后并未真正重建，现移到 CREATE 之前）；
  - `services/files.js`：read/write/remove 全部不再触碰路径字段，磁盘路径统一 `join(FILE_CACHE_DIR, fileId)` 推导；删除 `resolveStoragePath()`；
  - 新增回归测试 `test/test-file-storage-schema.mjs`（9 断言：老表重建保数据 / 幂等 / 古老 BLOB 表 DROP——子进程隔离验证）；全量 `node --test` **29/29 通过**；
  - 存量真实库（2 行附件元数据）在下次后端启动时自动完成重建。
- **v5：删除一次性 schema 迁移代码（用户确认真实库已升级后）**：
  - 实测启动后真实库 `file_storage` 列为 `file_id/mimetype/bytes/saved_at`（file_path 已移除，2 行数据完整保留，bytes 与磁盘文件一致）；
  - 按约定删除迁移②（file_path 列重建）与迁移①（古老 BLOB 表 DROP）：`db/sqlite.js` 仅保留最终 schema 的 `CREATE TABLE IF NOT EXISTS` + 索引；删除测试 `test/test-file-storage-schema.mjs`；全量回归 **28/28 通过**；
  - ⚠️ 若其他机器仍有**极老库副本**（含 `file_path` 或 BLOB `content` 列），新代码写入会因表结构不匹配报错，手工修复 SQL：
    ```sql
    -- 老表含 file_path / content 列时执行：
    CREATE TABLE file_storage_new (
      file_id TEXT PRIMARY KEY,
      mimetype TEXT,
      bytes INTEGER,
      saved_at DATETIME DEFAULT CURRENT_TIMESTAMP
    );
    INSERT INTO file_storage_new (file_id, mimetype, bytes, saved_at)
      SELECT file_id, mimetype, bytes, saved_at FROM file_storage;  -- BLOB 版无这些列时可跳过此行
    DROP TABLE file_storage;
    ALTER TABLE file_storage_new RENAME TO file_storage;
    CREATE INDEX IF NOT EXISTS idx_file_storage_saved_at ON file_storage(saved_at);
    ```
