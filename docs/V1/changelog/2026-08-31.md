## 背景：token 消耗分析（先分析后动手，2026-08-31）

针对"工具返回数据大、token 消耗高"问题做了全链路分析（runSqlAgent / buildSystemMessage / SKILL.md / 工具输出），核心结论：

| 内容 | 大小 | 每轮重发 | prefix cache |
|---|---|---|---|
| SKILL.md + 业务域清单（system） | ~7.6KB | 是 | ✅ 字节稳定，首轮后全命中 |
| 工具定义 ×5 | ~1.5KB | 是 | ✅ |
| get_sliced_index 表卡片输出 | ~10KB+/大域 | **历史累积** | 仅尾部新字节 |
| get_table_schema 输出 | 平均 ~2KB/表，最大 9.9KB（customer_clue_info） | **历史累积** | 同上 |

- **成本大头 = 工具结果体积 × 剩余轮数**（工具结果进历史后每轮全量重发），system 部分有 cache 兜底优先级低。
- 工具输出格式瘦身**只影响新产生的结果**，历史字节不变 → 不破坏 prefix cache（与 2026-08-25 方案 B"不折叠"决策兼容）。
- 结构性局限分析（哪些情况不可能输出正确 SQL）：枚举漂移（无数据采样工具）、schema 漂移（静态 DDL 文件与真实库无对账）、未文档化 JOIN 路径、无口径定义的派生指标、5.7 无递归 CTE、单条 SQL 无执行循环、行级数据权限无注入机制（`customer_clue_info.data_permission` 配置了但生成侧拿不到用户身份）、validate 仅有 R1/R2/R3/R5 结构级校验（语义全盲区）、F20 精简模式剥离索引信息（性能盲区）。**本日 §A 的 R6 EXPLAIN 对账即为其中"schema 漂移 + 性能盲区"两项的治理。**

## A. validate_sql_fields 增强：R6 EXPLAIN 真实库对账 + 紧凑 JSON（后端 / validators.js + toolFuncs.js）

### A1. R6 EXPLAIN 真实库对账

- **动机**：validate 原有 R1/R2/R3/R5 全是"对着同一份静态 DDL 文件"的结构校验，语义与真实库全盲。EXPLAIN 是全链路唯一能触达真实库的对账点：表/字段漂移（`ER_BAD_FIELD_ERROR` / `ER_NO_SUCH_TABLE`）直接暴露，顺带获得执行计划（治性能盲区）。
- **触发时机**：仅 R1-R5 静态校验**全部通过后**执行（用户要求"只有成功才能执行 explain"）；静态校验失败时不执行、返回结构无 `explain` 字段。
- **结果分级**：
  - `failed`（mysql2 语义错误码 `ER_*`）→ errors 追加 `R6_EXPLAIN`，`valid=false`，LLM 必须重写；
  - `ok` → `explain.plan` 压缩执行计划（`table [type] key rows Extra` 五列）+ `explain.warnings` 性能提示（type=ALL 且估算 rows>10 万 / Using filesort / Using temporary），**不阻断**；
  - `skipped`（DB 未配置/连不上/超时/被安全校验拒绝）→ 不影响 valid（生成可用性优先，`/execute` 仍有 sqlValidator 兜底）。
- **防注入三层**（用户硬性要求）：
  1. 复用 `/query/explain` 路由同一套 `validateReadOnlySql`：注释剥离、前缀白名单（仅 SELECT/INSERT/UPDATE/DELETE）、危险函数黑名单、多语句检测（sqlValidator.js 零依赖无循环 import）；
  2. 额外兜底拒绝 `INTO OUTFILE/DUMPFILE`、`LOAD_FILE(`；
  3. 连接池层 `multipleStatements: false`（mysqlPool.js:26）驱动级禁多语句；EXPLAIN 本身只走优化器、不执行语句、不加行锁。
- **兼容性**：llm.js registry 只读 `rawResult.valid/errors`（llm.js:1837-1838），新增 explain 字段无影响；前端 content 仍紧凑 JSON，ChatMessage 自动 pretty。
- **工具 description**（用户要求"不需要额外说明 explain，只要显示校验哪些"）：仅规则清单加一行 `R6 真实库 EXPLAIN 对账`，返回结构改为 `{valid, errors, summary, explain}`。
- 改动文件：`validators.js`（新增 `runExplainAudit` + 主流程第 6 步 + 头注释/入口注释更新）、`toolFuncs.js`（description）。

### A2. 返回内容改紧凑 JSON

- `validate_sql_fields` 原 `JSON.stringify(result, null, 2)`（pretty-print）与 `get_table_schema` 的紧凑策略不一致，errors 多时浪费 20-30% token，且该消息同样进历史每轮重发。
- 改为 `JSON.stringify(result)`；前端 ChatMessage.jsx:127 已有"紧凑 JSON → 自动 pretty 展示"逻辑，人类阅读不受影响。

### 验证

- GetDiagnostics 两文件 0 诊断；沙箱 Node v12 无法运行项目代码（`?.` 语法），功能验证需重启后端：
  1. 正常 SQL（含 LIMIT）→ valid=true 且带 `explain.plan`；
  2. 真实库不存在的字段 → `R6_EXPLAIN` 错误（valid=false）；
  3. 停用 MySQL 配置 → `explain.status='skipped'`，valid 不受影响。

## B. get_table_schema 剔除冗余 table_name（后端 / toolFuncs.js）

- 现象：返回结构外层 key 已是表名（`"edu_video_address": {...}`），内层还有 `"table_name": "edu_video_address"`，纯冗余。
- 根因：`table_name` 来自各 field_config JSON 文件头部（145 个文件均有），`getTableSchema` 合并时原样带出。
- 修复：`toolFuncs.js` `getTableSchema` 合并 field_config 后 `delete result.table_name`（工具层统一剔除，不动 145 个配置文件）。
- 注意区分：返回结构中的 `name` 字段（2026-08-24 恢复）**保留**——它服务前端人类阅读自描述，与本次剔除的配置文件冗余 `table_name` 不是一回事。
- 验证：模拟合并逻辑确认输出 keys 无 `table_name`；全工程无代码消费 schema 返回的 `table_name` 字段。

## C. field_aliases 去重清单（数据清理 · 工具生成报告 + 用户手工修改）

- 背景：field_aliases 大量条目与 DDL COMMENT 完全相同（alias 即注释复制），是 get_table_schema 输出冗余的重要来源。
- 产物：**[docs/field_aliases-去重清单.md](../../field_aliases-去重清单.md)**（临时比对脚本扫描后已删除脚本）。
  - 扫描 145 个 field_config vs 对应 DDL 注释（比对规则：忽略空白/大小写/全角斜杠）；
  - 命中 **35 个文件、81 处**重复，预估每次 get_table_schema 调用省约 868 字符（含 JSON 开销）；
  - 每行给出：字段 / field_aliases 现值 / DDL 注释 / 建议改后（数组删空则整条删除）；
  - DDL 无注释的字段不在清单（alias 有价值，保留）。
- 执行方式：用户按清单手工修改 field_config（少数条目仅大小写差异，如 `"一级部门ID"` vs 注释 `一级部门id`，删否自定）。
- 状态：报告已交付，**配置修改由用户进行中**；改完后可删除清单文件。
