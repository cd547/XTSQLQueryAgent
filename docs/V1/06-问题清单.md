## A. 当前确认的问题与风险（2026-08-12 核对）

### A1. /generate 非 stream 模式请求悬挂（P1）

- 位置：`backend/src/routes/query.js` POST `/generate`
- 现象：`schemaMode` 不为 `"stream"` 时，try 块内无 else 分支返回，请求既不响应也不超时报错，客户端挂起直到自身超时。
- 影响：前端始终传 `"stream"`，线上不触发；但接口语义不完整，任何调用方传错值都会挂死（且占用进程资源）。
- 建议：非 stream 分支改为显式 `400`/`501`，或实现一次性非流式调用（复用 `callLlmForFavorite` 类似逻辑）；历史评审 0723 P0-2 记录过该问题。

### A2. 默认 Node v12 与 better-sqlite3（Node 24 ABI）不匹配（P1，环境）

- 位置：`backend/node_modules/better-sqlite3`（NODE_MODULE_VERSION 137）；本机 PATH 上 node 为 v12.18.4（版本 72）。
- 现象：直接 `npm run dev:backend` 报 “compiled against a different Node.js version”；Electron 打包后若 `NVM_HOME` 未设置，后端也无法启动。
- 影响：新接手者按 README 直接 `npm run dev` 大概率失败。
- 建议：README/操作手册明确 Node 24 要求；本机设置 `NVM_HOME=D:\nvm`；或将 Electron 的 Node 探测逻辑改为可配置（如 `XTSQL_NODE_PATH` 环境变量优先）。

### A3. Electron 启动时强杀 5002 端口进程（P1，安全/稳定性）

- 位置：`electron/main.js` `killProcessOnPort`（win32 用 `netstat -ano | findstr ":5002"` + `taskkill /F /PID`）
- 风险：若 5002 被**其它无关服务**占用，会强制杀死该进程；`netstat` 文本解析也可能误匹配。
- 建议：改为先探测 `/api/health` 判断是否为本项目后端，是则保留/复用，否则提示用户手动处理，不要自动强杀。

### A4. messages 表随 SSE 事件膨胀、历史加载无分页（P1，性能）

- 位置：`routes/query.js`（每条 chunk/usage/tool/tool_return/LLM 日志都 INSERT）、`routes/session.js` GET `/:id/messages`（全量 SELECT *）
- 现状：实测 338 会话 10028 行 messages；单会话长对话可达数百行；LLM 工具日志全量入库。
- 影响：历史回显慢、SQLite 文件膨胀、token 统计遍历开销。
- 建议：为历史回显加分页/限制（如前 200 条 + 按 round 折叠）；或把 tool/LLM 日志改为独立表/抽样保留；评估 `messages` 行级 TTL。

### A5. `lastMessages` 全局缓存未按用户隔离（P2，安全）

- 位置：`services/llm.js` `lastMessages` / `setLastMessages`；调试接口 GET `/api/query/messages`
- 现状：任何登录用户（非生产 + admin 门槛）可读到**最后一位提问者**的完整 messages；CC 与 Responses 路径共享。
- 缓解：生产 404 + 非生产 admin 门槛已生效。
- 建议：改为按 `(userId, sessionId)` 索引，或直接移除该调试接口。

### A6. SQLite 与 Skill 文件写并发无锁（P2，一致性）

- 位置：`routes/skill.js` 的 `/save`、`/add-tag`、`/create-table-files` 直接 `fs.writeFileSync` 写 `table_index.json` 等文件
- 风险：多管理员同时操作（或保存与外部编辑并发）可能互相覆盖；`saveTableIndex` 已改为不写内存缓存、靠 md5 感知，缓解但未消除文件级竞态。
- 建议：引入文件写锁（如单进程内存队列/互斥），或对 table_index 改为原子写（写临时文件 + rename）。

### A7. 业务域索引与目录不一致：`report` 未注册（P2，功能）

- 位置：`skills/sql-creator-skill-v2/`：`domains/report.json` 存在，但 `domain_router_index.json` 未注册。
- 影响：`get_domain_index` 不展示 report 域，`get_sliced_index(["report"])` 查不到该域的表（agent 无法路由到 report 域表）。
- 建议：将 report 注册进 `domain_router_index.json`（或删除孤儿文件），并加启动期一致性校验。

### A8. tokenizer BPE 同步阻塞事件循环（P2，性能）

- 位置：`services/tokenizer.js` `bpeEncode`（同步循环，上限 10000 次迭代）
- 影响：大文本 token 计数（如每次保存 llm_messages 时对全量 messages 计数）可能阻塞 Node 事件循环。
- 建议：异步化/分批/缓存，或限制计数文本长度（如截断到 N 字符后再计）。

### A9. `llm_messages` 全量 JSON Blob 存储（P3，设计冻结项）

- 位置：`services/llm.js` `saveMessagesToDb`/`loadMessagesFromDb`；历史评审 PERF-6 标注 DESIGN-FROZEN。
- 影响：每轮全量序列化 + 全量反序列化；会话越长开销越大；`message_tokens` 每次全量重算。
- 建议：如需优化，改为按轮增量存储或压缩存储（gzip），并评估 DeepSeek prefix cache 对“上下文稳定”的依赖。

### A10. 错误响应透传内部细节（P2，安全）

- 位置：多处 `res.status(500).json({ error: e.message })`
- 影响：数据库/文件/第三方 API 的错误信息可能泄露内部路径、表结构、堆栈片段。
- 建议：生产环境统一返回通用错误码，明细仅入日志。

### A11. 用户名枚举（P3，安全）

- 位置：`routes/auth.js` register 返回 409 “用户名已被占用”；login 已统一提示但响应语义仍可区分（成功/失败）。
- 建议：注册接口改为通用提示；可选对用户名做同响应延迟。

### A12. 执行路径 SQL 校验为“正则+白名单”级（P3，安全纵深）

- 位置：`services/sqlValidator.js`（执行/EXPLAIN 前置校验）vs `services/sqlParser.js`（仅 validate_sql_fields 工具使用 AST）
- 影响：复杂语法绕过（如利用合法 SELECT 中的边缘写法）理论上存在空间；危险函数黑名单为枚举式。
- 建议：将 node-sql-parser AST 解析纳入执行路径（解析失败即拒绝），与 LLM 自检工具共用。

### A13. /config/test 每次新建连接（P3，性能）

- 位置：`routes/config.js` POST `/test` 每次 `mysql.createConnection`。
- 建议：复用连接池或限制测试频率。

### A14. 前端 App.jsx 单文件过大、状态分散（P3，可维护性）

- 现状：仍有 ~250 行 SQL tab 管理 + ~80 行 EXPLAIN AI 分析 SSE 流 + 多会话并行流式状态未抽离。
- 建议：候选抽 `useMultiSessionStreaming`（将 `messagesBySession` / `streamBatchesRef` / `isGlobalStreamingRef` 抽到独立 hook，−150 行，**中等风险**）；或继续推进 `useSqlTabs` / `useExplainAnalysis`。

### A18. `agent_timeout_ms` 配置未生效（P2，功能）

### A19. compactConsumedToolResults 折叠会“复活”被拦截/失败的工具消息（P2，一致性）

- 位置：`services/llm.js` `compactConsumedToolResults`（CC 与 Responses 路径共用）
- 现象（2026-08-13 日志实证）：同一会话先查 course 域、再问“当月新增线索数量”，`get_sliced_index(["crm"])` 被会话级剪枝拦截并写入 `Error: 已剪枝` 的 tool 消息；随后该消息进入“已消费历史区”，折叠逻辑**不看原消息内容**，仅凭 `tool_call_id → domain_ids=["crm"]` 重新从 `domains/crm.json` 生成真实表列表并覆盖错误消息 → 模型在思考中误以为调用成功（“Yes! The previous tool call … returned: …”）。
- 影响：跨问题场景可能把上一问题/其它域的数据“复活”进当前上下文，造成域外数据污染或域路由自欺；本次结果碰巧正确（CRM 数据真实），但语义上是程序伪造了一次成功的工具调用。
- 修复（2026-08-13，两个子项均已处理）：
  ① `compactConsumedToolResults` 折叠前跳过 `Error:`/`🚫` 开头的 tool 消息，不再“复活”被拦截/失败的结果；
  ② 域路由状态改为**问题级**：新问题清空 `slicedDomains/tableSchema/termConfirmed/userChoiceAsked`（`resetRegistryForNewQuestion`），允许重新路由新域；`request_user_choice` 中断后的续问保留状态（检测最后 user 消息紧邻的 `<!--user_choice:` tool 标记）；`getDomainIndexCalled` 保持会话级特例（内容少且会话内不变，一次即可，新问题复用）。
- 待观察：`checkAndFilterDuplicateCall` 的 fresh 域过滤逻辑（只加载新域）仍被“问题级剪枝”覆盖——同问题内先切 course 再想切 crm 仍会被剪枝拦截，但该场景属同一问题内的域扩展，可按需再评估是否放行。

### A20. sanitizeMessagesForLLM 告警噪音与中断残留（P3，改进项）

- 位置：`services/llm.js` `sanitizeMessagesForLLM`；触发于 `loadMessagesFromDb`
- 说明：`saveMessagesToDb` 在工具结果写回前保存，中断窗口（停止/断连/超时/进程退出）会留下"assistant 带 tool_call 但无 tool 响应"的悬挂状态；下次加载补合成响应并打 `warn: Sanitizing incomplete assistant tool_calls`。属预期防御（避免 DeepSeek 400），但 DB 中已有 13 行此类脏数据（6/11-8/12），每次打开都会刷 warn。

  4. 前端：聊天输入区模型标签改为"我的模型"，普通用户提供选择入口；ConfigPanel 的 admin 全局配置保持不变。
